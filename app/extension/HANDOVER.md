# フリマコピー（自作）项目交接说明

> 本文档写给接手本项目的 AI 编程助手：动手改代码之前先通读，尤其是「红线」和「平台要点」两节——里面的规则大多是踩过坑、用实测换来的，不要凭直觉推翻。
> 用户本人负责在 Windows Chrome 里更新扩展并实测；你的改动应小步、可验证。

## 这是什么

用户自研的 Chrome 扩展（Manifest V3，纯 JavaScript，**没有构建步骤**），用途：在 Mercari、ラクマ（Rakuma）、PayPayフリマ、Yahoo! Auctions 四个平台之间互相复制出品（读取商品页 → 到目标平台出品页自动填表）。当前版本 **0.10.9**（以 manifest.json 的 version 为准，每次发布递增）。

用户以「加载已解压的扩展程序」方式安装。**更新流程是手动的**：覆盖扩展文件夹 → 在 chrome://extensions 点重新加载（↻）。已打开的标签页仍跑旧的内容脚本，必须刷新页面才生效——排查「改了没效果」时先想到这条。

## 文件地图

| 文件 | 职责 |
|---|---|
| `manifest.json` | 权限与内容脚本注入表。host_permissions 含 `http://127.0.0.1/*`（与管理程序联动用） |
| `background.js` | Service Worker：GitHub Gist 指令轮询、本地管理程序任务轮询、可配置的 Mercari Todo 定时扫描、图片重抓，以及 Yahoo 未落札商品全分页再出品 |
| `lib/store.js` | `window.FurimaCopy`：暂存数据（chrome.storage.local 的 `copyData` / `copyImages`）、商品页的「📋 この商品をコピー」按钮与悬停菜单、各平台出品页 URL（SELL_URLS）、复制时抓取图片字节 |
| `lib/fill.js` | `window.FurimaFill`：React 安全赋值（setNativeValue）、按标签/占位符找字段、图片附件、结果面板 `showPanel`、自动填充监视器（autoTarget，带页面稳定判定）、页面状态快照下载（诊断用） |
| `readers/*.js` | 四个平台商品页的读取器，各自输出统一的暂存数据结构 |
| `fillers/sell-*.js` | 四个平台出品页的填充器，读暂存数据填表并逐项验证 |
| `popup.html` / `popup.js` | 设置：Gist 远程指令、管理程序联动，以及 Todo 扫描开关与分钟/小时间隔 |

暂存数据（copyData）主要字段：title / description / price / categoryText / conditionText / imageUrls / sourceUrl / sourcePlatform，以及联动用的 inventoryCode（管理程序的商品番号）和 managerTask 标记。

## 三种工作模式（数据流）

1. **手动复制→填充**：商品页点复制（或悬停菜单选目标平台，会先保存再跳转出品页）→ 出品页自动填充或点「📥 コピー内容を入力」。**只填不提交**。
2. **Gist 远程重上架**：外部把指令 JSON 写进一个 secret Gist，background 轮询到新指令后自动打开 Mercari 商品页复制、打开出品页填充。仅支持 Mercari→Mercari。**只填不提交**。
3. **管理程序任务**（selling-goods-manager，另一个项目）：扩展轮询 `http://127.0.0.1:17341` 的任务接口。type 为 `relist` 的任务按「参照商品 URL」走浏览器复制逻辑（不读本地图片文件），填完后按任务里的 `autoSubmit` 决定是否自动点「出品する」。**自动提交只允许出现在这种任务里**。

## 红线（不要违反）

- **绝不自动提交**，唯一例外是管理程序任务且任务自带 `autoSubmit: true`。不要给手动流程或 Gist 流程加自动提交，哪怕看起来很方便——这是用户明确划的界线。
- **干净室原则**：本项目是某付费扩展的自研替代品。禁止参考、移植、改写那个扩展的源码（分析材料不在本仓库内），只能借鉴功能概念，代码必须原创。
- **填充成功只认表单实际显示**。结果面板的 ✅ 会撒谎（历史上出现过：面板报成功但分类选错了相邻项、图片实际 0 张却报成功、实际选对了却报失败）。任何填充步骤的成功判定都必须回读表单的真实值/图片预览再下结论；改验证逻辑时用严格匹配，不要用「包含子串就算过」这种宽松判定（Mercari 分类验证现在用的是拼接字符串包含判定，就是为了防相邻同名分类的假阳性）。
- **不要收窄 content_scripts 的 matches**。Mercari 和 PayPay 是整站注入 + 脚本内按 pathname 门控，历史上收窄匹配曾导致复制按钮消失。确需调整时，先说明范围变化并让用户确认。
- **Mercari 图片**：其 CDN（static.mercdn.net）对程序化 fetch 一律 403，所以图片必须在复制时就从页面抓下字节存进 `copyImages`。填充时只有 `copyImages.sourceUrl === copyData.sourceUrl` 才允许用缓存图片，串图比缺图更糟。
- **PayPay 的 `__NEXT_DATA__` 在 SPA 站内跳转后仍是上一个商品的数据**。readers/paypay.js 按当前 URL 的商品 ID 校验数据节点（v0.8.11），校验失败时重新 fetch 当前页 HTML。不要改回「抓到节点就用」的写法。Mercari 读取器同理给 URL ID 命中的对象加了高权重。

## 平台要点

- **Mercari**：分类（/sell/categories）和状态（/sell/conditions）是独立 SPA 页面，需要往返跳转；**图片最后填**（往返会打断附件）。分类选择顺序：层级逐级点选（只接受精确匹配）→ 搜索框 → 推荐候选；推荐候选有防误点规则（叶子名太通用如「その他」时必须同时含父级名，v0.8.10）。分类/状态选完或失败后要用 `backToSellForm()` 回到表单页再继续后续步骤。管理程序的 Mercari 任务由 background 定向发送给刚打开的出品标签页，避免其他旧出品页抢占共享自动填充请求；填充回报与提交守卫均校验任务 ID（v0.10.3）。提交成功后优先从“出品した商品を見る”链接提取新商品 ID，不点击链接，并校验其不同于来源商品。
- **PayPayフリマ**：分类选择器有 PC（#sell-category-pc）和 SP（#sell-category-sp）两套预渲染 DOM，操作前先确认选择器真的打开了，且所有查找/点击必须限定在当前打开的 picker 容器内（v0.8.7）——在全文档范围找选项曾点到表单侧元素、还往标题里追加过分类名。最终验证只认表单行显示的叶子名。深层（4 级）分类路径待用户复测。
- **ラクマ**：分类是「カテゴリから探す」手风琴弹窗，逐级展开点选，成功标准是表单按钮显示完整路径（v0.8.1）。Rakuma 的完整闭环已多轮验证通过，不要随意动它的填充器。
- **Yahoo! Auctions**：商品说明读取要走页面的说明块 DOM——JSON-LD 里的 description 是被截断的摘要（v0.8.3）；分类读取用说明行/面包屑的链接文本以 " > " 拼接（v0.8.4），不要用 specValue（它把链接文本无分隔拼接）。分类填充和「希望落札価格」是手动的，这是设计如此，不是缺陷。
- **同平台才自动选分类和状态**；跨平台只给出候选值供用户手动选。状态词表四个平台基本通用，唯独顶级不同：Yahoo 是「未使用」，其他三家是「新品、未使用」。跨平台的精细化（富文本说明还原等）用户已明确叫停，不要主动去做。

## 调试方法

- 语法检查：`node --check <file>`（无测试套件）。
- 每次填充的结果报告会写入 chrome.storage.local 的 `lastFillReport`（自动提交另有 `lastSubmitReport`），控制台日志统一前缀 `[FurimaCopy]`。
- 结果面板上有「🔍 ページ状態を保存」按钮，可把当前页面状态下载成 JSON，是远程诊断的主要手段（让用户点它并发文件，比让他贴整页源码可靠）。
- 在你自己的云端/沙盒浏览器里无法登录 Mercari 等平台做实测（会被风控拦），实测只能靠用户在他本人的 Chrome 里完成。描述测试结论时注明平台、字段、扩展版本。
